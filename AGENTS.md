# AGENTS.md — easy-digital-book

Этот файл фиксирует контекст брейнсторминга по проекту `easy-digital-book`,
чтобы можно было вернуться к текущей точке рассуждений в будущей сессии, не
восстанавливая её заново. Статус на момент написания: **дизайн ещё не
завершён** — прошли этап брейнсторминга (approaches + часть design-секций),
формальная спецификация и план реализации для самого приложения (в отличие
от NovLang) ещё не написаны.

## О проекте

Пользователь искал инструмент для быстрого превращения текстов новелл,
которые есть у него на руках, в удобный для чтения формат под Kindle
Paperwhite. Существующие инструменты (связка FB2 Editor + Calibre, Sigil)
показались избыточными — они охватывают гораздо больше, чем нужно для этой
узкой личной задачи. Отсюда решение сделать собственный минималистичный
редактор — **easy-digital-book**.

Позже цель расширилась: сделать это open-source проектом, доступным всем,
не только личным инструментом.

## Ключевые решения (зафиксированы, пересматривать только с явной причиной)

- **Целевой формат вывода — EPUB.** Выбран как достаточно универсальный
  формат для Kindle Paperwhite.
- **Входной формат — не готовые файлы, а собственный редактор.** Пользователь
  пишет/редактирует текст прямо в приложении на языке разметки **NovLang**
  (см. ниже), а не импортирует готовый txt/html/docx. Конвертация "чужих"
  форматов на входе — вне рамок v1.
- **Один проект = одна книга.** Никакой библиотеки из нескольких книг внутри
  приложения в v1 — сознательно выбранный узкий скоуп.
- **Технологический стек — Tauri + Rust (ядро) + Vue 3.** Выбран путь
  "сразу на Tauri" (десктоп-приложение под Windows/macOS/Linux с первого
  дня), а не веб-SPA с десктопом "когда-нибудь потом". Причины:
  - Кросс-платформенный open-source десктоп был явным требованием, а C#
    (WinForms/WPF) не подходит — только Windows; Avalonia тоже отклонён,
    так как означал бы полностью отдельный UI-стек (XAML) вместо Vue.
  - Rust обязателен как язык ядра Tauri (сборка приложения без Rust-тулчейна
    невозможна), но писать собственный Rust-код в основном не потребуется —
    типовые нужды (диалоги открытия/сохранения файла, чтение/запись файлов)
    покрываются готовыми официальными плагинами Tauri с JS-обёртками.
    Кастомный Rust понадобится только для возможностей, которых нет в
    готовых плагинах.
  - Генерация EPUB (zip/XHTML) выполняется на стороне JS (JSZip), а не в
    Rust — чтобы код было проще переиспользовать и он не зависел от
    нативного слоя.
- **Формат хранения проекта — собственный файл-контейнер `.edb`.**
  Это zip-архив, содержащий:
  - файлы глав на NovLang (один файл = одна глава);
  - `manifest.json` — метаданные книги (название, автор, язык, обложка,
    порядок глав);
  - папку ресурсов (изображения, обложка).

  Выбран вместо хранения в браузерном IndexedDB/localStorage, потому что
  такой файл одинаково работает и на десктопе, и (потенциально) в
  веб-версии, легко бэкапится, версионируется в git, пересылается другим
  людям как обычный файл.

## Связь с NovLang

NovLang — язык разметки новелл и его парсер — выделен в **отдельный
подпроект**, разрабатываемый в отдельной директории/репозитории со своим
циклом спецификация → план → реализация. easy-digital-book **зависит** от
NovLang как от библиотеки (скорее всего, npm-пакет), но не содержит её
исходный код.

Что решено про NovLang (кратко, детали и промпт для планирования — в
`parser.md` в этом же репозитории):

- Язык реализации — **TypeScript** (не Rust/WASM — сочли избыточным).
- Публичный API из двух независимых слоёв: `parse(source) → { document, diagnostics }`
  и `renderToHTML(document, options)`, где `options.xhtmlMode` переключает
  вывод в строгий XHTML для EPUB.
- Грамматика v1: заголовок главы (`#`), курсив/полужирный, сцен-брейки
  (`***`), изображения (`![]()`), сноски переводчика (`[^1]` / `[^1]: ...`),
  блок-цитаты/письма (`>`).
- Философия ошибок: парсер никогда не бросает исключения, невалидный ввод
  даёт лучший из возможных результат + список `diagnostics` (warning).
- Тестирование — Vitest, юнит-тесты по каждому правилу грамматики +
  snapshot-тесты рендерера.

Полный контекст для запуска планирования NovLang — см. `parser.md`.

## Не решено / следующие шаги брейнсторминга по easy-digital-book

Дизайн самого приложения (в отличие от NovLang) пока проработан только
частично. При возврате к проекту стоит продолжить именно отсюда:

- **UI/UX редактора.** Не решено: layout (сплит-панель источник/превью?
  единая WYSIWYG-подобная область? вкладки по главам?), как именно
  синхронизируется live-preview с текстом на NovLang.
- **Управление проектом файлов.** Не спроектированы конкретные flow
  "Новый проект / Открыть .edb / Сохранить" через Tauri fs+dialog API,
  обработка ошибок при повреждённом или невалидном `.edb`.
- **UI редактирования метаданных книги** (название, автор, язык, обложка) —
  не спроектирован.
- **Пайплайн генерации EPUB.** Решено, что используется JSZip и вывод
  NovLang-рендерера в `xhtmlMode`, но не спроектированы: структура
  `manifest.opf`, spine, генерация TOC/nav (EPUB3 navigation document),
  обработка обложки как EPUB cover-image, валидность итогового EPUB.
- **Экспорт на устройство.** Предполагается, что v1 ограничивается
  сохранением `.epub`-файла на диск (перенос на Kindle — вручную, через USB
  или Send to Kindle), интеграция "отправить на Kindle" не обсуждалась и не
  включена в скоуп — стоит явно подтвердить/отклонить.
- **Тестирование и обработка ошибок самого приложения** (не NovLang) —
  не обсуждались вовсе.
- **Формальная спецификация не написана.** Всё выше — результат
  диалога-брейнсторминга (`superpowers:brainstorming`), не committed
  design-документ. Следующий шаг — либо сформировать полноценный spec-файл
  (`docs/superpowers/specs/...`) по итогам, либо продолжить design-секции
  (UI, файловые операции, EPUB-пайплайн) и только потом писать спецификацию
  и переходить к `superpowers:writing-plans`.
